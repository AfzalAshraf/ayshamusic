# Aysha Music — Rust Windows candidate (early milestone)

This is a separate native Rust/egui desktop candidate, **not yet a complete clone**. It has a dark/rose interface, search, selected-song playback, pause/resume/stop and previous/next controls, backed by the existing Rust catalogue and Rust audio path. It does not use a browser, Node, Python, an external Aysha server or the Android Media3 bridge. API calls are dispatched **in-process** through the Rust router, with no local HTTP port. Audio uses Rust/CPAL and Windows system audio; no playback test on an actual Windows machine has been performed.

The desktop data path is `%LOCALAPPDATA%\AyshaMusicRustDesktop`, separate from Android. Telegram/account setup and archiving, album art, icon picker, playback modes, seek, volume, automatic continuation, preferences migration, packaging/installer, UI parity and other Android features are **not implemented** in this candidate. Previous/next require an available session queue/history; searches and playback depend on the provider and can fail. No provider requests occur during automated CI. There is no updater and no automatic release publishing. The `.exe` is an unsigned CI artifact and Windows SmartScreen may warn about it; only run it if you trust the source and artifact.

Build on Windows (Rust and MSVC C++ build tools installed): `cargo build --release --manifest-path windows-app/Cargo.toml`. The Windows CI builds and runs offline tests; it is not a claim of physical speaker output or complete feature parity. The first lockfile is generated by CI; pin and commit it before production distribution.

## Local files and online limitations

Use **Open M4A file** to play a compatible local M4A/AAC file (up to 64 MB), including one copied from your phone. The app only reads the file; it does not import, upload, or delete it. This works independently of the online provider. A provider HTTP 403 is now reported clearly; this change does **not** fix or bypass an online provider refusal. Windows playback remains unverified on physical hardware.

## Sharing diagnostics

After an error, choose **View error report** to review it, or **Copy error report** and paste it into your support conversation. Reports hold up to 10 errors from this app session and are not sent automatically or saved to disk. They include the app version, architecture, player state, operation, backend status and recognized source/error codes. Unknown raw error text is intentionally omitted; provider messages, song/search details, file paths, URLs and credentials are not intentionally included. Review before sharing. Reports cannot capture a crash before the interface starts. Clear errors or restart the app to clear the in-memory history. This is diagnostics, not a fix for provider 403 errors.
